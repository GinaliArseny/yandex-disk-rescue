# Спасение данных с Яндекс.Диска

Готовая утилита в `scripts/`: Python 3.8+ только на stdlib (без pip), локальный сервер с веб-страницей
(порт `8765` по умолчанию), состояние в SQLite. Пользователь вставляет ссылки, видит прогресс и табло
«спасено / потеряно / с превью», а агент управляет тем же через HTTP API.

Не пиши свою качалку с нуля: в этой учтено много неочевидного поведения Яндекса и окружения
(см. «Что проверено опытом»), и каждое из этих знаний стоило часов отладки.

Во всех командах ниже используются переменные — выставь их один раз:

```bash
WORK=~/yadisk-rescue            # рабочая папка: app.py, index.html, state.db, server.log
PORT=8765                       # порт сервера
B=http://127.0.0.1:$PORT        # адрес API
```

## Быстрый старт

0. **Не запущен ли уже сервер?** `curl -s -m 3 $B/api/state >/dev/null && echo УЖЕ РАБОТАЕТ`.
   Если отвечает — это, скорее всего, экземпляр пользователя: **работай с ним**, второй не запускай.
   Если `$WORK/state.db` уже есть — сервер раньше запускали отсюда: запусти там же, он продолжит с места.
   Отдельный второй экземпляр — только с другим `PORT` и другой папкой (`DB_PATH`); утилита сама
   откажется стартовать на занятом порту или на уже открытой базе.
1. **Спроси, куда качать.** Это решает пользователь, не ты. Типичные варианты:
   - **NAS / сетевая шара** — `/Volumes/<share>` (macOS), `/mnt/...`, `/media/...` (Linux);
     смонтировать её должен сам пользователь (macOS: Finder → `Cmd+K` → `smb://<ip>`), пароли не вводи;
   - **внешний HDD/SSD** — `/Volumes/<Диск>`, `/media/<user>/<Диск>`, `D:\` и т.п.;
   - **этот компьютер** — например `~/YandexBackup`.
   Сервер сам находит подключённые тома (`GET $B/api/destinations`) — покажи пользователю список
   со свободным местом. Разным ссылкам можно задать разные места.
2. **Объём.** Для **папки** публичный API Яндекса размер не отдаёт (`size` пустой) — объём становится
   известен только после обхода: добавь ссылку (можно сразу поставить её на паузу,
   `/api/jobs/<id>/pause`), дождись `walk_status: done` и смотри `bytes_total` в `/api/state`.
   Не влезает — скажи до загрузки: исключить тяжёлые папки или выбрать другой диск. Страница сама
   предупредит «может не хватить места»; помни, что битые файлы места не займут.
3. **Рабочая папка:** `mkdir -p $WORK && cp scripts/app.py scripts/index.html $WORK/` (каталог скилла
   может быть только для чтения; база и лог появятся рядом с `app.py`).
4. **Запусти сервер долгоживущим процессом**, с логом в файл:
   ```bash
   cd $WORK && PORT=$PORT nohup python3 app.py >> console.log 2>&1 &     # Windows: py app.py
   sleep 3; curl -s -m 3 $B/api/state >/dev/null && echo ЗАПУЩЕН || cat $WORK/console.log
   ```
   Если не стартовал, причина в `console.log` (например, «Порт … занят»). Рабочий лог сервер пишет
   сам в `$WORK/server.log` (`tail -50 $WORK/server.log`). Если качать на сетевой том
   или внешний диск **на macOS**, процесс агента может не иметь к ним доступа (раздел ниже) — тогда
   попроси пользователя запустить `cd ~/yadisk-rescue && python3 app.py` в своём терминале
   (Terminal.app или встроенная терминальная панель) и управляй дальше через API — он тебе доступен.
   Пока есть что качать, сервер сам запрещает сон (caffeinate / systemd-inhibit /
   SetThreadExecutionState) и снимает запрет, когда всё скачано или пауза. **Скажи пользователю**:
   компьютер не уснёт, пока идёт загрузка, а крышку ноутбука закрывать нельзя — тогда уснёт всё равно.
5. **Добавь ссылки** — пользователь вставляет их на странице и выбирает «Куда качать», или ты
   через API с полем `dest`. Сервер сам проверит, что в папку можно писать, и вернёт `error`, если нет.
6. **Открой страницу** пользователю: `open http://localhost:$PORT` (macOS), `xdg-open` (Linux),
   `start` (Windows).

Потоков по умолчанию 16. Для NAS по SMB разумно 16–32 (больше 32 не ставь: при сбое сети smbfs на Mac
может зависнуть), для локального или внешнего диска — до 32–64. Скорость в основном упирается не в
потоки, а в долю битых файлов на стороне Яндекса.

### macOS: «Operation not permitted» / «нет прав на запись»

Процесс агента (например `com.anthropic.claude-code`) часто не имеет TCC-доступа к **сетевым томам,
съёмным дискам и папкам «Загрузки», «Документы», «Рабочий стол»** — `ls` падает с
`Operation not permitted`, хотя всё смонтировано и права есть; в `/api/destinations` такой том будет
«нет прав на запись». Варианты: сервер запускает пользователь в своём терминале (шаг 4), выбрать
локальную папку вне защищённых (`~/YandexBackup`), либо пользователь выдаёт доступ в
«Конфиденциальность и безопасность → Файлы и папки / Полный доступ к диску».
Проверить, кому отказано: `/usr/bin/log show --last 2m --predicate 'subsystem == "com.apple.TCC"'`.

## Управление через API

Все POST — с `Content-Type: application/json` (иначе 403: защита от чужих вкладок браузера).

```bash
curl -s $B/api/destinations     # куда можно качать: тома + этот компьютер, свободное место, ok/ошибка
# добавить ссылки в выбранное место (текст любой — ссылки вытащатся регуляркой); priority — вне очереди
curl -s -XPOST -H 'Content-Type: application/json' $B/api/jobs \
  -d '{"urls":"https://disk.yandex.ru/d/AAA https://disk.yandex.ru/d/BBB","dest":"/Volumes/T7/YandexBackup","priority":true}'
curl -s $B/api/state            # jobs (+dest_free, dest_short, bytes_left, error), dests, active, speed, awake, broken
curl -s $B/broken.tsv           # реестр битых (он же пишется в каждое место назначения: <dest>/_broken.tsv)
curl -s -XPOST -H 'Content-Type: application/json' $B/api/settings -d '{"workers":32}'    # 1..64
curl -s -XPOST -H 'Content-Type: application/json' $B/api/settings -d '{"paused":true}'
# по ссылке #ID: pause | resume | retry (перепроверить битые) | prioritize | unprioritize | delete
curl -s -XPOST -H 'Content-Type: application/json' $B/api/jobs/3/retry -d '{}'
# сменить место назначения (уже скачанное останется в старом месте); delete убирает только запись, не файлы
curl -s -XPOST -H 'Content-Type: application/json' $B/api/jobs/3/move -d '{"dest":"/Volumes/T7/YandexBackup"}'
# исключить / вернуть папку верхнего уровня ссылки (файлы получают статус excluded)
curl -s -XPOST -H 'Content-Type: application/json' $B/api/jobs/1/exclude -d '{"path":"/Видео"}'
```

Пауза **мягкая**: новые файлы не берутся, а уже начатые докачиваются — `active` пустеет за несколько
секунд (крупные файлы — дольше). Пауза переживает перезапуск сервера.

Если ссылка не открылась (опечатка, снята с публикации, доступ только приглашённым), у неё в
`/api/state` заполнено `error` с понятным текстом, а в карточке на странице — красная плашка.
Когда очередь опустела и все обходы завершены, страница показывает «✓ Готово» с итогом, местами
файлов и подсказкой про реестр и «Повторить битые» — пересказывать это пользователю необязательно.

Сводку для пользователя считай из `/api/state` по всем `jobs`: `files_ok`/`bytes_done` — спасено,
`files_failed`/`bytes_failed` — потеряно, `files_preview` — из потерянных есть превью,
`files_left` — очередь. Выживаемость = ok / (ok + failed) по файлам и по байтам.

## Держи руку на пульсе

Загрузка при сбоях Яндекса идёт часами, и пользователь обычно уходит. Если он просит следить
(или прогон долгий) — проверяй состояние каждые 10–15 минут: инструментом отложенной проверки или
мониторинга, если он есть в твоём окружении, иначе при каждом возвращении пользователя. Одна проверка:

```bash
curl -s -m 5 $B/api/state > $WORK/.state.json || echo "СЕРВЕР НЕ ОТВЕЧАЕТ"
python3 - "$WORK/.state.json" <<'PY'
import json, sys; s = json.load(open(sys.argv[1])); J = s["jobs"]
print("пауза:", s["settings"]["paused"], "| скорость %.1f МБ/с | активно %d" % (s["speed"] / 2**20, len(s["active"])))
print("спасено %d, потеряно %d (с превью %d), очередь %d" % tuple(sum(j[k] for j in J)
      for k in ("files_ok", "files_failed", "files_preview", "files_left")))
for d in s["dests"]:
    if not d["ok"]: print("МЕСТО НЕДОСТУПНО:", d["path"], d["error"])
for j in J:
    if j["error"]: print("ССЫЛКА:", j["url"], j["error"])
    if j["dest_short"]: print("МОЖЕТ НЕ ХВАТИТЬ МЕСТА:", j["dest"])
    if j["walk_status"] == "failed": print("ОБХОД УПАЛ:", j["url"])
PY
# причины сбоев за 15 минут, сгруппированные по типу (текст до двоеточия)
sqlite3 $WORK/state.db "select substr(reason, 1, instr(reason || ':', ':') - 1) r, count(*) from files
  where status='failed' and updated > strftime('%s','now')-900 group by r order by 2 desc"
```

| Что видно | Что это и что делать |
|---|---|
| Сервер не отвечает | Процесс умер (закрыли терминал, Mac уснул, перезагрузка). Запусти той же командой — продолжит с места |
| `пауза: True`, место недоступно | Автопауза: отвалилась шара/диск. Попроси пользователя переподключить, проверь запись, сними паузу (`{"paused":false}`). Файлы, на которых это случилось, уже в очереди |
| `HTTP 500 … (временный сбой — повторится)` | Сбой сервиса скачивания Яндекса, не битый файл. Когда очередь опустеет, сервер **сам один раз** повторит все такие файлы (в логе: «повторяю N файлов…»). Ничего делать не нужно |
| Всплеск `Сеть…`, `API недоступен`, `ERROR` | Моргнули сеть/VPN — тоже временное, тоже попадёт в автоповтор. Если сбоев много и связь уже вернулась, можно вернуть сразу: `sqlite3 $WORK/state.db "update files set status='queued', attempts=0, reason=NULL where status='failed' and (reason like 'Сеть%' or reason like 'API недоступен%' or reason like 'ERROR%' or reason like 'HTTP 5%')"` |
| `ССЫЛКА: … не открывается` | Ссылка мертва или с опечаткой — попроси у пользователя актуальную; старую можно удалить (`/delete`) |
| `пауза: True`, но `активно` > 0 | Нормально: пауза мягкая, начатые файлы докачиваются |
| Скорость ~0, очередь есть, все активные «ждут заголовки» | Норма при массовых сбоях: потоки отсеивают битые файлы. Проверь, что растёт «потеряно»/«спасено» |
| Скорость ~0, активных нет, очередь есть, паузы нет | Что-то не так — `tail -50 $WORK/server.log` |
| `МОЖЕТ НЕ ХВАТИТЬ МЕСТА` | Предупреди: исключить тяжёлые папки или сменить место (`/move`) |
| `NO_RESPONSE` / `PARTIAL` растут | Это и есть потери на стороне Яндекса — не чинится, просто фиксируй в отчёте |

Докладывай коротко: спасено / потеряно / очередь, что нашёл и что сделал. Не перезапускай сервер
без причины (незавершённые обходы начнутся заново) и не меняй логику загрузки посреди прогона, не
собрав цифры (см. «Диагностика» ниже).

## Как устроено (чтобы правильно объяснять пользователю)

- **Обход** ссылки в ширину: файлы корня встают в очередь первыми; непрочитанная папка → `LIST_FAIL`.
- **Очередь:** сначала приоритетные ссылки, внутри — файлы ≤200 МБ, крупные потом.
- **Каждый файл сверяется по md5** с метаданными Диска; несовпадение не принимается.
- **Крупные (≥32 МБ) — кусками в 8 соединений** через Range, план кусков в `<файл>.part.json`
  пишется до первого байта → докачка после любого обрыва корректна. Общий лимит соединений
  под куски — 48.
- **Битый файл** уходит в реестр с причиной; для фото рядом кладётся превью
  `<имя>.preview.jpg|png` (до 1280 px), оригинал остаётся в реестре — «Повторить битые»
  позже докачает его и удалит превью.
- **Временные сбои** (HTTP 5xx, сеть, API) — когда очередь опустела, один автоповтор; новые ссылки
  и «Повторить битые» взводят его снова.
- **Автопауза:** ошибка записи в место назначения (EACCES/EIO/ESTALE/ENOENT…) не делает файл битым —
  файл возвращается в очередь, всё встаёт на паузу до ручного «Продолжить».
- **Один сервер на порт и на базу**: при занятом порту или уже открытой `state.db` второй экземпляр
  выходит с объяснением, не трогая очередь.
- Перезапуск безопасен: состояние в SQLite, скачанное пропускается по размеру, незавершённые обходы
  перезапускаются.

## Что проверено опытом (октябрь 2026, массовая недоступность файлов на части узлов хранилища)

Подробности, замеры и форма ответов API — в `references/yandex-behavior.md`. Кратко:

- **Бьются отдельные файлы, а не узлы.** Узел `sNNNklg.storage.yandex.net` отдаёт одни файлы
  за 0.4 с и молчит по другим. Помечать «мёртвый узел» нельзя — это рубит живые файлы.
- **Живой узел отдаёт заголовки за 0.38–0.52 с** → таймаут на заголовки 5 с (не 45).
- **Повторы молчащего файла бесполезны** (2-я попытка спасает ~1%, 3-я — 0) → одна попытка,
  остаток — «Повторить битые» в конце.
- **PARTIAL:** узел отдаёт первые N байт и закрывает поток, докачка с N даёт 0 байт —
  хвост файла потерян. Бывает и N = 0: `206`, но тело пустое (`IncompleteRead` — это
  `http.client.HTTPException`, не `OSError`; не поймаешь — поток куска умрёт молча и md5-проверка
  выбросит весь скачанный файл). Сегментная загрузка иногда вытаскивает куски из «молчащих» файлов.
- **HTTP 500 от сервиса скачивания** (`downloader.disk.yandex.ru`) встречается пачками — временное,
  лечится повтором позже.
- **Превью** живёт на отдельном сервисе: максимум 1280 px (XXXL), больший размер не отдаётся;
  HTTP 434 — превью не существует (в вебе Диска битая иконка), спасти нечем; для PNG превью — PNG.
- **Веб-интерфейс Яндекса тоже не скачивает такие оригиналы** — это не проблема клиента.
- `DiskNotFoundError` (404) при живой с виду ссылке — почти всегда ошибка публикации
  (ссылку перевыпустили или доступ «только приглашённым»). Проверка: `<title>` веб-страницы
  «Ничего не найдено — Яндекс Диск». Две ссылки могут вести на одну папку — сравни `resource_id`.
- **Скорость в МБ/с обманчива:** на мелких файлах она падает, хотя файлов/мин много — смотри
  счётчик «ф/мин»; серверный ETA завышен, т.к. битые выпадают без скачивания.

## Грабли окружения

- **SMB-клиент macOS может намертво зависнуть** (процессы в состоянии `U`, Finder висит,
  `umount -f` не помогает) при ~100 параллельных записях и сетевом сбое. Держи потоки ≤32,
  не подключай шару повторно поверх зависшей (`home-1`) — лечится перезагрузкой. После неё:
  `sqlite3 $WORK/state.db "pragma integrity_check"`, затем верни в очередь сетевые сбои (SQL из таблицы выше).
- Сервер живёт, пока жив его процесс: не закрывать терминал/хост-приложение. Сон сервер запрещает
  сам, но закрытая крышка ноутбука всё равно его усыпит.
- Проверено на macOS; Linux должен работать; Windows поддержан в коде, но вживую не проверялся —
  на Windows будь внимательнее к первым минутам прогона.
- VPN/прокси меняет скорость с живых узлов, но не «оживляет» битые файлы.
- Остановить сервер: `kill $(lsof -t -iTCP:$PORT -sTCP:LISTEN)` (или `Ctrl+C` в его терминале).

## Диагностика: куда уходит время

```bash
curl -s $B/api/state | python3 -c '
import json,sys,collections; s=json.load(sys.stdin); a=s["active"]
print(collections.Counter("качает" if x["speed"]>0 else ("ждёт заголовки" if x["host"] else "API") for x in a))'
sqlite3 $WORK/state.db "select status, attempts, count(*) from files where updated > strftime('%s','now')-1800 group by 1,2"
sqlite3 $WORK/state.db "select substr(reason, 1, instr(reason || ':', ':') - 1), count(*) from files where status='failed' group by 1 order by 2 desc"
```

Если почти все потоки «ждут заголовки» — ты тратишь время на битые файлы; проверь таймауты
и число попыток, а не канал. Перед изменением логики собери такие цифры — интуиция здесь
дважды ошибалась.

## Чего не делать

- Не вводить пароли NAS и не создавать аккаунты — монтирует пользователь.
- Не удалять файлы в месте назначения; исключение папки только снимает её с очереди.
- Не принимать файл без совпадения md5 и не считать битым файл, упавший из-за ошибки записи в место назначения.
